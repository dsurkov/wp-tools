# WP Tools

**WP Tools — набор CLI-инструментов для обслуживания WordPress**

```bash
curl -sSL https://gist.githubusercontent.com/dsurkov/efafe42477aa571139401628d2fafd5a/raw/wp-tools.php | php -- packager woocommerce
```

## Что это / для чего

Stateless-набор CLI-инструментов для админа множества сайтов: один
самодостаточный PHP-файл, который запускается прямо на сервере WordPress
(через `curl | php` или установленный исполняемый файл), находит WP-инсталляцию
по `wp-load.php` и выполняет обслуживающие операции. Ничего не устанавливается
в сам WordPress: код живёт только в процессе PHP.

## Инструменты

| Инструмент  | Статус        | Описание                                        |
|-------------|---------------|-------------------------------------------------|
| `packager`  | Доступно      | Пакует установленные плагины и темы в ZIP-архивы и выдаёт download-ссылки |
| `backupper` | В планах      | Бэкап файлов и базы данных сайта               |

## Установка / два способа запуска

Оба способа используют **один и тот же скрипт** — код не ветвится. Разница
только в том, как файл попадает в PHP: по сети в stdin или с диска.
Запуск — из корня сайта или любой поддиректории (корень WP ищется подъёмом
вверх от текущей директории).

### Способ 1 (рекомендуется для постоянных сайтов): файл вне docroot

```bash
curl -sSL https://gist.githubusercontent.com/dsurkov/efafe42477aa571139401628d2fafd5a/raw/wp-tools.php -o /usr/local/bin/wp-tools
chmod +x /usr/local/bin/wp-tools
wp-tools packager woocommerce
```

Файл лежит **вне веб-корня** — веб-сервер его не отдаёт и не исполняет.
Обновление — повторный `curl -o` (или `git pull`, если положить файл в
репозиторий). Установленный файл можно один раз аудировать: он детерминирован
и не меняется между запусками.

### Способ 2 (разово / без установки): curl | php

```bash
curl -sSL https://gist.githubusercontent.com/dsurkov/efafe42477aa571139401628d2fafd5a/raw/wp-tools.php | php -- packager woocommerce
```

Ничего не пишется на диск. Удобно для одноразовых операций и демо; для
прод-сайтов предпочтителен Способ 1 (см. «Безопасность»).

## Использование

Верхнеуровневые команды:

| Команда           | Действие                                  |
|-------------------|-------------------------------------------|
| `packager <slug>` | Запаковать плагин/тему по слагу           |
| `list`, `-l`      | Показать доступные инструменты            |
| `help`, `-h`      | Показать справку                          |

Флаги `packager`:

| Флаг        | Действие                                        |
|-------------|-------------------------------------------------|
| `--list`, `-l` | Показать установленные плагины и темы       |
| `--all`, `-a`  | Запаковать все плагины и темы               |
| `--help`, `-h` | Справка по packager                         |

Пример вывода (`packager --list`):

```
=== AVAILABLE PLUGINS AND THEMES ===

PLUGINS (slug / version)                  | THEMES (slug / version)
------------------------------------------+-------------------------------------------
woocommerce (8.9.3)                       | twentytwentyfour (1.2)
```

## Возможности packager

- Поиск корня WordPress подъёмом от текущей директории — работает из любой поддиректории сайта.
- Список установленных плагинов и тем со слагами и версиями.
- Упаковка по слагам, всех сразу (`--all`) или по списку слагов.
- Архивы кладутся в `_packages/` внутри корня WP — веб-доступная папка.
- Для каждого архива печатается прямая download-ссылка (`site_url()/_packages/<slug>-<version>.zip`).
- Slug в имени архива очищается от недопустимых символов; пустая версия → `0.0.0`.

## Требования

- **PHP 7.2+ (CLI)** — скрипт проверяет версию и завершается с понятной ошибкой на старых PHP.
- Расширение **ZipArchive** (проверка: `php -m | grep -i zip`).
- **curl** — только для Способа 2.
- **SSH-доступ** к серверу.

> Важно: CLI-версия PHP на cPanel-хостингах может отличаться от веб-PHP
> (версия, набор расширений). Проверяйте именно CLI: `php -v`,
> `php -m | grep -i zip`.

## Подводные камни

- **CLI-php ≠ веб-php**: на shared-хостинге `which php` покажет CLI-бинарь; веб-PHP может иметь другие расширения. Расширения проверяются у runtime-CLI, а не у веб-PHP.
- **CLI без ZipArchive**: скрипт честно сообщает об ошибке — проверяйте `php -m | grep -i zip` заранее.
- **`--` обязателен** при `curl | php`: `php -- packager …` — иначе `packager` будет воспринят как аргумент самого php.
- **Большие сайты**: упаковка всего сайта (`--all`) может упереться в лимит памяти — запускайте `php -d memory_limit=-1`.
- **Reverse-proxy**: `site_url()` за прокси может отдать неверный домен/схему — download-ссылка тогда не откроется снаружи; проверяйте на конкретном хосте.
- **Права на `_packages/`**: SSH-пользователь и веб-пользователь могут различаться; если папку создаёт SSH-юзер, веб может не отдать файлы (и наоборот).
- **Публичность ссылок**: ссылки на архивы в `_packages/` публичные (если папка отдаётся вебом) — удаляйте папку после скачивания (скрипт сам об этом напоминает).

## Безопасность

- Требуется **шелл-доступ**: инструмент исполняет код в контексте пользователя, от которого запущен — давайте доступ только доверенным администраторам.
- **Прямой HTTP-доступ запрещён**: файл отдаёт только справку и завершается (в CLI-режиме он и не исполняется вебом). Держите установленную копию вне docroot.
- **`curl | php` — supply-chain риск**: код исполняется сразу из сети. Если используете этот способ, пините raw-ссылку по коммиту (`raw/<hash>/...`), а не по ветке.
- **Установленный файл предпочтительнее для прод-сайтов**: аудируется разово и детерминирован — между запусками ничего не меняется.
